# 块、行与对象头

## 尺寸

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `BLOCK` | 32 KiB | 堆发放的单位，按自身大小对齐 |
| `LINE` | 256 B | 块内复用的单位（每块 128 行） |
| `GRANULE` | 8 B | 分配对齐；对象大小是整数个粒 |
| `LARGE` | 16 KiB | 超过半块的对象单独分配 |
| `LARGE_MMAP` | 64 KiB | 从这么大起，大对象单独 `mmap` |
| `HEADER` | 24 B | 私有对象头 |

块按 32 KiB 对齐，所以任何对象地址抹掉低 15 位就是它所在的块。

## 块头

每个块在数据区之外记着：

- **行标记**：每行一个 `u32` 纪元。行的标记比上一次完成的纪元旧，就是空闲行，所以从来不需要清标记，新的回收换一个更新的
  纪元就行；
- **对象起点位图**：每个粒一位，每个对象的第一个粒置位。清扫和跨堆查找都靠走这张图找对象；
- 状态（空闲、正在分配、可回收利用、满、已清扫）和疏散用的计数。

分配缓冲把它在同一个位图字里分配的对象起点位攒起来，用一次原子 OR 发布。发布的时机是：换到别的字、接手另一个块，或者
`mutate` 返回时。在那之前没有人读这些位：下次回收之前，缓冲独占自己的块。

## 块从哪来

在 Linux 上：

- 每个堆自己映射 2 MiB 的大段，切成对齐的块；
- 还回来的块先进**热池**、保留内存，因为下一轮多半还要这么多块；
- 热池满了才 `madvise(MADV_DONTNEED)` 把内存还给系统，地址进冷池等待复用。先发热池里的块；
- 堆析构时解除这些大段的映射。

这里绕开了 glibc：对齐分配要多花代价，而且还给 glibc 的内存不会还给系统。

在 macOS、Windows 和 Miri 下，块从全局分配器来。

## 对象头

私有对象以 24 字节的 `Header` 开头：

| 字段 | 位数 | 含义 |
| --- | --- | --- |
| mark | 32 | 最后一次标记它的回收的纪元；疏散期间用到 `FORWARDED` / `BUSY` 位 |
| info | 32 | 粒数（24 位）、引用计数（6 位）、奇偶位、大对象位 |
| visit | 64 | 类型的 `unsafe fn(*mut u8, &mut Tracer)`：追踪或改写它的边 |
| drop | 64 | `Option<unsafe fn(*mut u8)>`，析构函数；搬走之后这里存转发地址 |

前两个字（`Core`）跨堆对象也有。跨堆对象的 16 字节 `PHeader` 不存函数指针，而存类型号和出生戳。因此两种堆的块、行、
清扫、标记用的是同一套代码。

单个对象的数据最多 128 MiB（24 位粒数）。
