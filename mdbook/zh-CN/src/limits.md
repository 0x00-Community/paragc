# 限制与未解决的问题

本页列出 paragc 还没做的事，以及设计上吃紧的地方。依赖跨堆之前请先读一遍。

## 私有堆

- **不扫栈。** 回收后要活下来的对象都必须能从 `Root`、`Far` 或入口走到。
- **单个对象最多 128 MiB。** 对象头用 24 位粒数记大小。
- **`Slot` 是两个字**：值，和引用计数上次计的值。
- **没有并发年轻回收。** 年轻回收再短也是一次停顿。
- **按地址索引的结构**在指着年轻对象期间必须自己也是年轻的（见[年轻回收](young.md)）。
- **一条不稳定的测试**：`gc::background_release_while_mutating`，release 构建下。

## 跨堆

- **不会死的元数据。** 类型表和指针图只增不减，违反[核心宗旨第 1 条](principles.md)。

- **只有全停回收。** 跨堆没有并发标记、年轻回收、引用计数和疏散。`collect` 要等每个活进程的 mutator 离开，所以一个活着但
  卡在 `mutate` 里的进程会让回收停住。只有死进程会被跳过。
- **不压缩。** 跨堆对象从不搬动，碎片只能靠复用行和给空块打洞来缓解。
- **64 个窗口。** 堆号就是 1 TiB 地址区里的窗口号，所以一个目录最多同时有 64 个活的跨堆，每个堆最大 16 GiB。
- **`CrossHeapRef` 的登记**只由一起回收归还。频繁改写它们的代码要定期做一起回收。
- **信任。** 映射了堆的进程可以读写整个堆。没有逐对象的保护，也没有锁。几个进程同时写，不保证一致性；这是有意的选择，
  线程语义预期由上层语言提供。
- **死掉的进程**可能留下几个用不了的块或入口（死在领到之后、记下之前）。
- **出生戳**撞上的概率约 2⁻²⁷，所以过期的弱引用或签名极少数情况下会解析到同一地址上同类型的新对象。

## 晋升

- **固定地址区每个进程一个。** `reserve_fixed` 用 `MAP_FIXED_NOREPLACE` 在 64 TiB 处映射 1 TiB。那里已经有东西就会失败，
  一个进程也只能占一次。
- **挂着跨堆时关掉了并发标记**，年轻疏散强制为 `Full`。做晋升的运行时放弃了 paragc 最短的停顿。
- **碰到不可共享的边会 panic。** 可共享对象经追踪的边走到不可共享对象，回收器会 panic。这是编程错误，但它在回收器里暴露，
  而不是在写入的那一刻。
- **只归主人回收的跨堆会一直长到完整回收。** 年轻回收往里晋升，但从不在里面释放。只有 `Heap::collect` 回收跨堆垃圾，
  所以主要做年轻回收的运行时也必须安排完整回收。
- **匿名跨堆是私有的。** `create_anonymous` 只在本进程可见。想让别的进程读自己对象的运行时，必须建文件堆并传出描述符。
- **短暂的不可见窗口。** 写进跨堆槽的私有对象在下一次年轻回收前仍是私有的，在别处读出来是空。

## paragc 之上的对象模型（j8）

共享一个 JS 值，接收方必须看懂对象的布局，而不只是它的字节。j8 现在的情况：

| JS 对象的组成 | 放在哪 | 能否共享 |
| --- | --- | --- |
| 字符串 | GC 堆，字节在对象尾巴里 | ✓（j8 #49 起） |
| shape（属性名、属性特性、转移） | GC 堆，经 [handle](handles.md) 引用（j8 #55） | ✗（handle 是私有的，还带析构） |
| 属性值（内联槽、store） | GC 堆 | shape 能共享之后才行 |
| 字典模式的属性 | 存着 `Vec`、`HashMap` 的 GC 对象 | ✗ |
| 函数 | 字节码和内联缓存在每个函数一个的 GC 对象里（j8 #55） | ✗ |
| 宿主对象 | `Box<dyn Any>` | ✗；经信箱请主人代办 |

**难点曾经在 shape。** shape 的身份到处被比较：内联缓存要比，JIT 还把它写死在机器码里（`CheckShape`）。如果身份就是地址，
shape 做成普通的、会搬家的 GC 对象，这两样都会坏。候选方案：

1. ~~**永不回收、放在固定位置的 shape。**~~ **否决**：违反[核心宗旨第 1 条](principles.md)，没有永生的东西。
2. **shape 作为会搬家的 GC 对象。** 内存能回收，但缓存要持有能被追踪的引用，JIT 需要一个搬家后不变的身份。
3. **晋升时另做一份可共享的描述。** 热路径不变，但每个对象多一个字，之后再加属性时两边都要同步。
4. **shape 放在不搬家、但照样回收的空间里。** 这需要钉住分配。

j8 选了方案 2，靠 [handle](handles.md) 让它可行：shape 用 `alloc_handle` 分配，身份是 handle id，shape 搬家时 id 不变。缓存和
生成的代码比较 id；持有它们的编译好的函数也是 GC 对象，所以没人再引用时，shape 和代码一起被回收。

**共享还差什么。** handle 只存在于私有堆，`Shape` 还带析构，所以晋升过去的对象，shape 字仍指着发送进程 handle 表里的一项。共享
普通对象（第 4 段）需要一个住在跨堆里的 shape。
